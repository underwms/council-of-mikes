# Using Council Workflows

Read manifest.json and load applicable specialist/workflow packages from the unified canonical skills directory. Announce workflow usage. Load metadata cheaply and detailed reference material only when needed.

Follow the actual platform instruction hierarchy and the user's task scope. Skills do not override platform instructions. Existing authorization for a reviewed design or implementation task is sufficient; do not repeat approval questions for each step.

Tool names are logical operations: read/edit files, run commands, track tasks, and delegate. The host adapter supplies available tools and its own reference mapping. Never assume a tool exists from its name in another platform's examples. Delegation may be sequential when unavailable.

Select brainstorming for new designs, systematic-debugging for investigations, writing-plans for approved multi-step implementation, and verification-before-completion for completion evidence. Use TDD where the selected profile and change require it. Load the applicable specialist contract before domain decisions.

Resolve source paths through manifest.json and runtime paths through the selected profile. Execution policy and exclusions belong at host user scope; instruction text is not a substitute for native permissions configuration.
