# Council skill and context behavior checks

Use these checks after changing skill routing, startup, memory selection, or coordination. Keep installation checks and observed model behavior as separate results.

## Evidence and claim boundaries

Select evidence for the claim being made; do not promote one kind of pass into another. Record the inspected revision or source/diff fingerprint, fixture/environment, observed result and relevant limits. Apply the existing review contract; this table adds no automatic semantic gate or new approval round.

| Evidence | Supports | Does not establish |
|---|---|---|
| Source audit and lock | Governed bytes, supported structure/links, strict UTF-8 and selected content checks at the observed state | Every assumption is current, all guidance agrees, excluded content is approved, or a model followed it |
| Installation/placement check | The inspected files, native settings fragments and links resolve as checked | Hook trust/execution, loaded session state, or that a regular leaf file is a separate copy; inspect parent links and resolved paths |
| Native policy parser/matcher | Decisions for the supplied rules, modes, synthetic inputs and included checks | Every live admin/session setting, OS permission, tool execution, or authorization from the user to perform that task |
| Script regression | Assertions and dependencies actually exercised at the tested revision/fixture | Unexercised services, deployment, or model compliance with prose |
| Native model sample | The observed reads/delivery, decisions and attempted actions captured for that bounded turn | Every client/model/override, interactive compaction, unseen actions or a universal non-execution guarantee |
| Semantic review | Evidence-backed findings in the inspected scope, with correction history | Exhaustive consistency or absence of future defects; hashes and keyword checks cannot replace this review |

A native mode label or permissive rule is not an OS sandbox or a user task request. Preserve actual native restrictions and report the tested policy/permission scope separately from model behavior.

For an incomplete or timed-out turn, retain sanitized partial observations and fixture checks when available. If partial events were not retained, mark the affected reads, skill delivery and attempted actions unknown; an unchanged fixture only covers the fingerprinted roots. A narrower diagnostic or preference answer does not pass the broader timed-out scenario. Keep each attempt and its disposition rather than rerunning until a favorable result replaces it.

When stronger evidence contradicts an earlier interpretation, withdraw or narrow that claim, link the correction and preserve the original record. Reuse an older observation only with a stated applicability reason; do not present it as a fresh check or aggregate unrelated passes into universal readiness. Report scoped completion and separately unverified runtime flows without silently waiving required acceptance checks.

Explicit negation can cover coordinated action lists, such as do not start or resume. These are bounded fixture controls.

Startup and stale-context grades require delivery of the exact generated current-state body. A path mention, failed read or tracking IDs alone do not pass. A bounded English check also tests paused status and rejects sampled resume advice. These patterns do not establish general semantic understanding.

The Codex startup/stale passes in the historical 2026-11-12 codex-final.json report cannot establish these stronger criteria. Its sanitized report lacks the raw delivered bodies and answer text needed to regrade them. This does not prove that the model failed. ## Fresh native-client samples

The knowledge case samples a member using an isolated selected knowledge collection: `node scripts/council-eval.mjs --client codex --case knowledge --timeout-ms 180000`. It requires delivered Relay guidance, the shared use contract, the routed index/note/source evidence and pending proposal, plus the supported fixture topic/key and a qualified proposal status in the answer. Full delivered artifact bodies are matched in memory; only artifact labels and bounded outcome facts enter the report. This is sampled retrieval evidence, not proof for all members or models. It does not inspect service repositories or change accepted knowledge.

```powershell
node scripts/council-eval.mjs --client all --case all --timeout-ms 180000
node scripts/council-eval.mjs --client gemini --case startup --report work/gemini-startup.json
```

The runner starts fresh native Codex/Gemini CLI sessions with their configured default models and authentication. Codex uses its read-only sandbox, never-approve mode and ephemeral session option. Gemini uses its native plan mode; it does not provide an OS sandbox guarantee. Native trust, permissions and policies remain in force. The runner never invokes the custom Council engine, bypasses hook trust, installs clients, changes credentials, or alters service repositories.

Each case gets a new scratch workspace and selected private MemoryForge session containing synthetic current and paused tasks. Profile startup instructions must recover that namespace without an onboard prompt. Historical notes are deliberately older than the current summary. The cases cover automatic startup, stale history, FAIR routing, convening, quoted non-invocation and a small inline review. The read-only fixture constraints are deliberate safety controls: absence of engine execution in these trials is evidence for these constrained requests, not proof that the same result holds under every permission configuration.

Scoring uses native JSONL events, observed memory/skill reads, exact synthetic tracking-ID recovery, final-answer outcomes, attempted mutations/spawns and engine commands. A claim such as "Council loaded" alone cannot pass startup. Successful CLI exit alone cannot pass any case. Incomplete or unavailable native turns are blocked, observed violations are failed, and only satisfied sampled criteria are passed. These are behavioral smoke tests, not an exhaustive semantic judge. Inspect failures before changing guidance; do not weaken a criterion to manufacture a pass.

Positive skill evidence requires successful native activation or delivery of the complete canonical skill body, including when a later command in the same batch fails. A successful path mention, partial read or failed attempt alone does not count. Convening requires the coordination and brainstorming skills plus a concrete collaborative question; a printed call-sign alone is not evidence of the workflow, and equivalent behavior does not fail merely because a decorative label is absent. Reports fingerprint the evaluator revision so preliminary and reviewed runs remain distinguishable.

The report retains sanitized observations and reason codes. Raw messages, shell commands, tool arguments and payloads are discarded. Scratch workspaces and synthetic memory remain under central work/ and memory/workspaces/ for review; never reuse them as real task state. Use the same cases in fresh sessions after a model/client upgrade. Actual interactive compaction, client-specific UI discovery and persisted hook trust still require native checks; a fresh-process recovery sample does not certify those flows.

## Windows host qualification and native injection

Run Codex qualification from a normal supported client host. Launching a second native Windows sandbox inside an outer agent sandbox can fail before a file-read command starts. The observed failure is `CreateDesktopW failed for shared private desktop: 5`. A controlled native command/exec probe on 2026-11-12 failed inside the outer sandbox and passed outside it with the same Codex read-only sandbox policy. Treat an unmet loading check accompanied by this failure as environment-blocked; it does not establish a skill-selection defect. Unsafe actions still fail the case, and successful later delivery can satisfy the check after a recovered launch failure.

For agent-driven qualification, use the normal approved escalation mechanism to run the test process on the host while keeping Codex's own read-only policy and never-approve mode. Do not disable native sandboxing, bypass hook trust or modify managed security to make a test pass. Record host conditions and native launch failures separately from model behavior.

Compare ordinary trigger phrases with explicit native skill selection and, for integrations that own turn/start, a structured skill input item. The [official app-server skill interface](https://learn.chatgpt.com/docs/app-server#skills) accepts an absolute skill path and injects its instructions. Record accepted structured inputs separately from tool-mediated body reads; a valid native injection need not produce a file-read tool event. Include a text-only app-server control so a change of transport is not mistaken for an injection effect. Repeat identical cases with the same configured model and permissions, retaining every result rather than rerunning until one passes.

MCP text and structured-content wrappers may carry complete skill bodies. The evaluator decodes supported output wrappers for comparison against canonical skill content without persisting their raw payloads. A successful read attempt, an entry in skills/list or a printed role label still does not prove the full skill was delivered.

## Current memory maintenance

Maintain a registered task snapshot through tasks save, or current_state.md in an explicitly selected namespace, at meaningful milestones and checkpoints: date, current objective/status, verified facts with evidence pointers, open items and separately paused work. Keep it within 5,000 UTF-8 bytes. preferences.md holds stable user-confirmed preferences. Default startup reads stable preferences/knowledge routing and metadata-only suggestions until a task is selected. A bound task restores its snapshot; explicit workspace/session recovery retains the bounded legacy reader with handoff fallback. Historical backlog is not injected into unrelated chats. Existing historical files remain preserved. Follow the handoff skill for semantic updates; hooks must not invent the current objective from arbitrary assistant prose.

## Skill and role maintenance

Keep each skill description focused on its trigger and ownership boundary. Place detailed doctrine in the selected profile and task references, and read it only when relevant. Apply specialist skills inline by default. Use a separate native agent only for authorized bounded work with a concrete benefit from independent context, parallelism, or review; assign ownership and integrate the evidence. A role call-sign alone does not indicate that a separate agent ran.

## Reply behavior samples

Run `node scripts/council-eval.mjs --client all --case reply --timeout-ms 90000` on the supported host. Individual selectors are reply-clarity, reply-procedure and reply-evidence. The reply group contains three fresh, read-only cases per client. It uses the existing selected synthetic namespace and mutation checks. It does not ask the model to report or grade its review.

The cases ask for ordinary developer updates and an operator procedure. They assess preservation of facts and literal command names, removal of selected dense wording, backup order, failure stop conditions, uncertainty and narrow test evidence. Existing sentence-length and word-choice checks apply too. The grader uses bounded patterns; it is not a general semantic judge. It can reject valid alternatives or miss contradictions. Positive and negative controls test the recorded criteria, not complete English understanding.

Full delivery of shared.md must be observed before the combined case passes. This verifies delivery of its new review requirement, not private review execution. A good answer without this observed read passes its output checks but does not pass combined qualification. Prompt hooks or other unobserved delivery paths may still have supplied rules. Report this distinction rather than claiming the model ignored unavailable instructions.

Reports keep reason codes and sanitized observations. They retain no reply bodies, prompts or raw tool payloads. A pass is sampled output and instruction-delivery evidence. It does not establish causal improvement, consistent performance across turns, or full ASD-STE100 compliance. Preserve all attempts. Do not repeat failed model cases merely to obtain a pass.

Run `node --test scripts/tests/council-reply-behavior.test.mjs scripts/tests/council-eval.test.mjs scripts/tests/council-reply-standard.test.mjs` for grader controls and affected runner checks. These checks are distinct from live native samples.

## Answer-order cases

The reply group also includes reply-order and reply-order-unknown. Select either case directly for a fresh native sample. The existing native modes, fixture isolation, mutation checks and sanitized reporting still apply.

reply-order uses a fixed release record. It requires deployment status in the first prose block and the next action in the opening two blocks. Headings are ignored. Supporting test evidence must follow the action. Existing fact and uncertainty checks still apply.

reply-order-unknown requires unknown authorization and an action to ask the release owner. It rejects invented approval or rejection. An ordinary explanation remains outside these fixture-specific opening checks. There is no universal word-count threshold and no new completion-hook score.

These bounded patterns can miss semantic contradictions or reject valid alternatives. They do not establish general answer quality. A native output can pass while instruction delivery remains unobserved; keep both results separate. No raw response text is retained by this evaluator.

Codex reply, startup and stale cases grade the last delivered assistant message. Earlier progress messages do not define final answer order or task recovery. Other evaluation cases and Gemini streaming assembly keep their existing behavior. Initial answer-order samples that joined progress and final messages remain historical results with that grading limit.
